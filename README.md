# netorch — 流表更新的安全编排器

给云游戏机房做集中控制的网络，控制器一次要推几百条新流表；各交换机生效有先有后，
中间几百毫秒常出现环路、或者流量撞到还没装规则的交换机被丢掉，玩家就一卡。

`netorch` 就是那个编排器：输入每条流的旧路径和新路径，它算出一个**分轮下发、等确认**
的更新顺序，保证**任何一个中间时刻**每个报文要么走完整的旧路径、要么走一定能到终点的
路——不出环、不进黑洞、链路不超载。全部用 Python 实现，交换机和流量用事件驱动仿真。

---

## 快速开始

```bash
# 1. 看一次计划（相邻跳互换：没有单阶段安全顺序，必须两阶段）
python3 -m netorch.cli plan --scenario swap

# 2. 跑一次仿真，和"一股脑下发"对比
python3 -m netorch.cli simulate --scenario merge

# 3. 逐轮穷举验证：每一轮里命令的每一种生效顺序，是否都安全
python3 -m netorch.cli verify --count 60

# 4. 批量验收（几千次运行，输出 results/acceptance.json）
python3 -m netorch.cli accept --big --count 120 --runs 6 --fails 2

# 5. 生成回放页面（浏览器打开 results/replay-swap.html）
python3 -m netorch.cli demos
```

无第三方依赖，Python ≥ 3.9。测试：`python3 tests/run_tests.py`（357 项）。

## 核心安全模型

一条流有旧路径 `A` 和新路径 `B`，每条路径是"入交换机 → … → 末跳交换机"的简单路径
（主机不是交换机，末跳交换机用固定的出口端口发往目的主机，记作 `HOST`）。

每个交换机对一条流最多持有一条**生效规则**（或按版本号标记的两条）。报文在交换机
`x` 查它当时的规则，得到下一跳。要保证的不变量（每个时刻都成立）：

| 不变量 | 含义 |
| --- | --- |
| **INFLIGHT** | 网络里的报文永远不绕圈、不撞到没有规则的交换机 |
| **HOLDERS** | 任何还持有规则的交换机，沿它持有的规则都能到终点。持有"指向已删规则"的交换机会形成**潜在黑洞**——只有假设报文永不到达那里才安全，而确认/重传/缓冲让这个假设不成立 |
| **链路带宽** | 按最坏情况一时刻计：每个持有者都可能压着一个缓冲报文，沿自己的路径发 |
| **表项数** | 每个交换机持有的表项不超过它的容量；两阶段更新时同一条流在新旧路径上都占表项 |

**为什么按 HOLDERS 而不只按 INFLIGHT**：这正好对应真实硬件——交换机可以先"冻结某条流、
改规则、再放行"，前提是它手里的规则指向的下游都还有规则。HOLDERS 就是这个前提。

### 依赖规则

对一条流，设 `old(x)`/`new(x)` 是交换机 x 在旧/新路径上的下一跳，`changed` 是两者不同的
交换机集合：

1. **新路径下游先装**：新路径上任意两个 changed 交换机，下游的必须先于上游变。
   否则上游先改、指向还没改的下游，报文进入陈旧路径。
2. **旧路径上游先切**：旧路径上相邻的 `x→y` 若都被改，且 `x` 的新规则不再指向 `y`，
   则 `x` 必须先于 `y`。否则 `y` 先切走，还能从旧边 `x→y` 进来的报文就撞空。

这两条规则的**下闭集**（任意 subset，只要每个已改交换机的依赖都已改）都安全。这一点
用暴力枚举验证过：随机单流/多流、每一条流所有 2^k 个中间状态，**约 13 万个状态，0 违例**
（`tests/test_deps.py`）。反过来，规划器生成的每一轮（同一轮内命令可任意顺序生效），
它的**每一个子集**都安全——这是仿真里打乱生效顺序仍然 0 违规的理论依据。

### 轮次

- 一轮 = 一组命令，控制器**等这一轮所有 ack** 再发下一轮，所以轮内命令可能任意顺序生效。
  因此"某轮安全"要求它的**每个子集**都安全，等价于该轮是依赖 DAG 的一张反链、且前置都已提交。
- 依赖 DAG 可以**有环**（相邻跳互换就是：新路径要下游先、旧路径要上游先），此时不存在
  单阶段顺序。

### 两阶段（版本号标记）

有环时把相关流升级成两阶段：

1. **装**：新路径所有交换机装带版本号 1 的新规则，入口仍打版本 0 —— 这一步对网络不可见，
   任意顺序、任意子集都安全；
2. **切**：入口改成打版本号 1；
3. **等排空**：等长于旧+新路径长度的排空窗口，让还带版本 0 的报文走完旧规则；
4. **删**：删掉旧规则。

两阶段期间新旧规则**同时存在**，所以表项翻倍。规划器会算出**每台交换机的峰值表项数**，
超出容量时如实报告"两阶段规则装不下"，而不是偷偷超限。

### 带宽与临时中转路径

一条流在更新途中，最坏情况下旧规则和新规则都在，因此预留 `old ∪ new` 的整条路径。
两条流的最坏占用在某条链路上放不下时，就必须串行；如果**互相等待**（A 要等 B 让出
链路，B 又要等 A），就是容量死锁。这时借一条**临时中转路径**给其中一条流：
`old → 中转 → new`，让它先离开争用的链路，其余流正常推进，最后它再走上新路径。
中转路径本身就是一次普通的单阶段移动，同样受全部不变量约束。

### 下界

规划器的操作是**按 (流, 交换机)** 计数的，两条流在同一交换机上的命令互相独立。所以：

- 每条流至少需要它自己依赖链的长度（`dag_height`）；
- 最坏占用互斥的一组流（团）必须严格串行，至少是它们深度之和（`capacity_lb`）；
- 有两阶段流时至少 3 轮（`tagged_lb`）。

`lower_bound = max(三者)`，报告的 `gap = rounds - lower_bound`。仿真结果显示这些生成器下
gap 恒为 0。

### 交换机执行时间不确定 & 分批确认

仿真器给**每条命令**独立抽"下发延迟 + 生效延迟 + ack 延迟"，所以一轮里的命令生效顺序
完全打乱；控制器严格按 ack 门控发下一轮。删除规则的轮次前面还强制加排空窗口——因为
一个已经注入了的报文可能需要逐跳走出网络，删规则太快就会在半路把它删没了（真实丢包，
审计看不出来，只有逐包回放能发现）。这些都在 `netorch/sim.py`。

### 中途失败与安全退回

某台交换机更新到一半失败：控制器**等已经送达的命令落地**后，从**确认过的当前状态**出发，
用**运行时验证**算退路——每个候选步骤先在一份状态副本上跑全部不变量审计，只有安全才采纳，
还能把互相独立的命令合成一批（同样验证该批的每个子集）。失败交换机永不触碰。当前路径
已经穿过失败交换机的流"已经在丢包"，标为**豁免**而不是算作退路的违规；旧路径穿过失败
交换机的流标为**不可恢复**。

## 回放页面

`python3 -m netorch.cli demos` 生成 5 个自包含 HTML（数据内嵌，双击即开）：

- `results/replay-swap.html` — 相邻跳互换，用版本号两阶段；
- `results/replay-merge.html` — 两流汇聚，多轮串行；
- `results/replay-detour.html` — 容量死锁，临时中转路径；
- `results/replay-chain.html` — 依赖链；
- `results/replay-fail.html` — 中途故障 + 安全退回。

页面逐 tick 动画：蓝圈是这一刻变了的交换机，紫色是新路径、灰色是旧路径，点击交换机看
它这一刻对每条流转发的下一跳，顶部横幅在违规时刻变红。时间轴可拖、可播放。

## 代码结构

```
netorch/
  model.py       拓扑、流、逐流状态、不变量审计（INFLIGHT/HOLDERS/带宽/表项）
  deps.py        依赖抽取、SCC、拓扑分层
  planner.py     一阶段 / 两阶段 / 中转路径 / 下界 / 检查点自检
  retreat.py     故障后的运行时验证退路
  sim.py         事件驱动仿真（随机生效顺序、ack 门控、逐包回放）
  scenarios.py   随机拓扑与流生成、手工压力用例、中转族
  experiments.py 批量验收、指标汇总
  replay.py      回放页面生成与本地服务
  cli.py         命令行入口
tests/           357 项测试，含依赖规则与每轮每子集的穷举验证
```

主要 API：

```python
from netorch import Flow, Topology, Planner
from netorch.sim import RunningPlan, Timing

plan = Planner(topo, flows, drain_ticks=5).plan()
plan.stats.rounds, plan.stats.lower_bound, plan.stats.gap
for r in plan.rounds:
    print(r.index, r.kind, [str(o) for o in r.ops])

res = RunningPlan(topo, flows, plan.rounds, Timing(), random.Random(1)).run()
res.violation_ticks, res.packets_lost
```

## 已知边界

- 路径必须简单（真实控制器装的就是无环路径）；环路上的多路径等价类不在模型内。
- 带宽按最坏情况（持有者都可能压着一个包）保守估计，等价于"更新期间该流的流量要么全程
  旧路径、要么全程新路径"，不建模按流分片。
- 两阶段需要入口能按版本号标记报文（真实里可以是入口 AC/交换机上的标记寄存器）；表项
  翻倍由规划器显式核算并拒绝超容量。
- "入方向的中间命令一律先落地再退回"是刻意保守的选择；真实控制器也可以选择丢弃尚未
  下发的命令，但那样已送达的命令仍可能乱序生效，所以这里取最坏口径。
